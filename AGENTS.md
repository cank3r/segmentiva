# Segmentiva agent operating contract

This file governs every coding and review agent working in this repository.

## Sources of truth

1. `SEGMENTIVA_MVP_BUILD_PLAN.md` defines product scope, architecture, phases, acceptance criteria, and Shopify constraints.
2. `README.md` defines the public product promise and current project status.
3. Current official Shopify documentation decides implementation details that may have changed.
4. `docs/QA_DEPARTMENT.md` defines the QA workflow and release gate.

If an official Shopify source conflicts with the build plan, stop the affected work, link the source, explain the impact, and propose a plan update. Never silently work around a platform restriction.

## Delivery rules

- Work on one numbered MVP phase at a time.
- Do not introduce features from a later phase or the post-MVP roadmap.
- Preserve the conventions generated by Shopify's official React Router template.
- Use TypeScript strict mode, the GraphQL Admin API, and stable Shopify API version `2026-07`.
- Use the [Shopify AI Toolkit](https://shopify.dev/docs/apps/build/ai-toolkit) for all Shopify API and platform work, and verify Shopify surfaces against current documentation before implementing them. The toolkit is an editor/agent-host plugin (install it per that page, or `npx skills add Shopify/shopify-ai-toolkit --list` for skill-compatible hosts); the Shopify Dev MCP server is already wired for this repo in `.cursor/mcp.json`.
- Keep changes small, reviewable, and atomic.
- Do not invent command results, test evidence, API behavior, or manual validation.
- Do not claim a phase is complete until every acceptance criterion has evidence.
- Do not commit secrets, `.env`, access tokens, customer data, raw webhook bodies, raw GraphQL payloads, production identifiers, or dev-store exports.
- Never add Kliquea-specific IDs, domains, credentials, or theme assumptions to product code.

## Non-negotiable product invariants

- Segmentiva is multi-tenant. Every application-data access must be scoped to a verified shop.
- Customer-level preference data belongs primarily in Shopify app-owned metafields.
- The MVP must not persist customer names, email addresses, phone numbers, postal addresses, or raw customer profiles.
- Only exact tags owned by the `segmentiva:` namespace may be reconciled or removed.
- Published questionnaire versions are immutable; label changes must not alter stable internal keys.
- Shopify authentication, session storage, HMAC verification, and App Bridge setup must use official Shopify libraries and generated conventions.
- Customer-account calls require server-side verification of a fresh session token and binding to the expected shop and customer.
- GraphQL HTTP `200` is not proof of success: inspect `userErrors` and handle throttling explicitly.
- Webhook and synchronization handlers must be idempotent.
- Segmentiva does not replace Shopify authentication, intercept OTP codes, or inject fields into Shopify's native sign-in form.
- Preference collection is not marketing consent. Never preselect or imply email/SMS consent.

## Required implementation handoff

An implementation agent must report:

1. MVP phase and acceptance criteria addressed.
2. Files changed and why.
3. Commands run with exact pass, fail, or not-run status.
4. Manual Shopify validation still required.
5. Known risks, assumptions, and blockers.
6. Proposed atomic commit message.

Passing lint or tests does not replace requirement, security, privacy, accessibility, or Shopify-platform review.

## QA independence

Files under `.cursor/agents/qa-*.md` define independent reviewers. While acting as a QA reviewer:

- remain read-only;
- review the requested diff, not the developer's intentions;
- do not fix the code you are approving;
- cite file paths and line numbers whenever available;
- attach reproducible evidence to every finding;
- distinguish verified facts from assumptions;
- mark unavailable checks as `NOT RUN`, never as passed;
- do not lower severity because a fix appears easy;
- do not approve your own unverified inference.

## Finding contract

Every finding must contain:

| Field | Requirement |
| --- | --- |
| ID | Specialist prefix plus sequence, for example `SEC-001` |
| Severity | `P0`, `P1`, `P2`, or `P3` |
| Location | File and line, route, schema object, or configuration key |
| Evidence | Observed code, command output, or reproducible behavior |
| Impact | Concrete user, merchant, privacy, security, data, or operational consequence |
| Reproduction | Minimal steps or conditions that expose the problem |
| Recommendation | Smallest safe corrective direction, without editing the code |
| Regression test | Test or check that would prevent recurrence |
| Confidence | `high`, `medium`, or `low`, with uncertainty stated |

Severity means:

- `P0` — immediate release blocker: exploitable cross-tenant access, secret/customer-data exposure, auth bypass, destructive data loss, or equivalent incident-level risk.
- `P1` — release blocker: core journey broken, material security/privacy failure, invalid platform behavior, corrupt migration, or mandatory compliance failure.
- `P2` — significant defect or risk with bounded impact or a documented workaround; requires an owner before release.
- `P3` — minor usability, maintainability, observability, test-quality, or documentation issue.

## Release gate

The final gate is one of:

- `PASS` — required checks passed, no open `P0`/`P1`, and no unowned `P2`.
- `PASS_WITH_RISK` — no open `P0`/`P1`; every accepted `P2` has an owner, written rationale, and expiration or follow-up.
- `FAIL` — any open `P0`/`P1`, failed mandatory check, missing evidence for a sensitive path, or a required check incorrectly reported as passed.

Only the `qa-release-manager` issues the final gate. Human approval is still required for production release, data migration, protected-customer-data access, and Shopify App Store submission.
